## 2. 相图与交叉点

工具：[`../code/phase_diagram.py`](../code/phase_diagram.py)（代价模型 + 实测 `k(κ)`）

`n*(κ, s)`：11 位第一次超过 FP32 的矩阵阶数

| κ | s=2 | s=4 | s=8 |
|---|---|---|---|
| 1e6 | 1264 | 2528 | 5056 |
| 1e8 | 1760 | 3520 | 7040 |
| 1e10 | 1248 | 2496 | 4992 |
| 1e12 | 898 | 1536 | 3072 |

**两条规律**：
1. `n* ∝ s`（`s` 翻倍，`n*` 翻倍）——因为残差通路的代价是 FP64 定价的；
2. `n*` 随 `κ` **弱下降**（1e6 的 1264 → 1e12 的 898）——`κ` 大时 FP32 的迭代数涨得更快，
   11 位反而更早划算。

图：`figures/fig9_phase_n{256,1024,4096}.svg`

## 4. 平台 B：Mars X201 的 `s`（已实测）

工具：[`../code/lu_bench_gpu.cu`](../code/lu_bench_gpu.cu)（TILE=32 共享内存 GEMM，
`hc_runtime_api` 原生接口，带 `C[0][0]` 校验和自检）

| n | TP64 (GF/s) | TP32 (GF/s) | **s** | 自检 |
|---|---|---|---|---|
| n | TP64 (GF/s) | TP32 (GF/s) | TP16 (GF/s) | **s₃₂** | **s₁₆** | 自检 |
|---|---|---|---|---|---|---|
| 512 | 882.0 | 1728.8 | 1775.0 | 1.960 | 2.013 | ok |
| 1024 | 1172.6 | 2615.1 | 2686.5 | 2.230 | 2.291 | ok |
| 2048 | 1227.2 | 2774.2 | 2813.2 | 2.261 | 2.292 | ok |
| 4096 | 1238.3 | 2824.9 | 2874.9 | 2.281 | 2.322 | ok |
| 8192 | 1230.8 | 2817.3 | 2878.6 | **2.289** | **2.339** | ok |

**`s₃₂ = 2.29`、`s₁₆ = 2.34`**（TP16 = 半精度存储 + FP32 累加，不经过张量核）。

### 4.0 ★ 结论：没有张量核，11 位等于白降

半精度存储只带来 **2%** 的提升（2.289 → 2.339），因为乘加仍压在 FP32 单元上——
内存减半了，算力没变。**这一档的收益完全取决于是否存在 MMA 硬件路径。**

这直接改写 §5 的相图：`s₁₁` 在 Mars X201 上（按 TF32/FP16 非张量核路径）≈ `s₃₂`，
所以相图里"11 位"那块区域**在当前实现下不存在**；只有当内核真的用上 MMA 时，
`s₁₁` 才可能达到 `s₃₂` 的 4–8 倍，那块区域才会出现。

**给工程的一句话**：降精度要降在"有专用算力"的那一档上。只降存储不降算力，
在带宽受限的核上也许有用（本基准是算力受限），在算力受限的核上没有意义。

### 4.0b 把"设备"换成"实现"：11 位档的门槛 s₁₁*(κ,n)

11 位优于 FP32 ⟺ `1/s₁₁ < 1/s₃₂ − 6Δk/n`，即

```
s₁₁*(κ,n) = 1 / (1/s₃₂ − 6Δk/n)      有解当且仅当 n > 6·s₃₂·Δk
```

| κ | Δk | n 门槛 | s₁₁*(4096) | s₁₁*(16384) |
|---|---|---|---|---|
| 1e6 | 79 | 1,085 | 3.11 | 2.45 |
| 1e8 | 110 | 1,510 | 3.62 | 2.52 |
| 1e10 | 78 | 1,071 | 3.10 | 2.45 |
| 1e12 | 48 | 659 | 2.73 | 2.38 |

对照实测：`s₁₆ = 2.34` **够不到**（差 2%–17%），而张量核的 `s₁₁` 若在 8–16，**超出 3 倍以上**。

**这就是 §5 的新纵轴**：不是"哪台机器"，而是"你的 11 位内核做到多快"。
同一条 Mars X201，非 MMA 与 MMA 是两个不同的最优点。

图：`figures/fig10_s11_threshold.svg`

### 4.0a 尝试过但走不通：WMMA 张量核路径

想直接测 MMA 吞吐，结论是**这条 API 不可用**：

| 尝试 | 结果 |
|---|---|
| `grep -rn "namespace wmma"` | 无命中 |
| 编 `#include <hctlass/arch/wmma.h>` | ✅ 能编（`.o` 产出） |
| 内核里用 `nvcuda::wmma::fragment` | ❌ `error: use of undeclared identifier 'nvcuda'` |

原因：`hctlass` 里所有 `nvcuda::wmma::` 的引用都在 `#if __CUDA_ARCH__ >= 750` 块内，
而 `htcc` 目标的宏不是 NVIDIA 的 arch 值，整块被跳过。`wmma.h` 能编只是头文件解析通过。

**建议的三条替代路线（按成本排序）**：
1. **用 `hcblas` 的 HGEMM**（`-lhcblas` 在你们的链接列表里）——如果它内部派发到张量核，
   直接测 `hcblasHgemm` vs `hcblasDgemm` 就得到 `s₁₁`，不需要写内核；
2. 用 `hctlass::gemm::device::Gemm` 实例化一个 half GEMM（模板库，编译重）；
3. 查厂商规格书拿 TF32/FP16 峰值，与实测 `s₁₆=2.34` 一起作为 `s₁₁` 的上下界。

**注意**：§5 的门槛表 `s₁₁*(κ,n)` 不依赖这个测量——它给的是"内核要打到多少"，
实测值只是用来判断"当前实现够不够"。所以论文可以先定稿。

### 4.1 两个平台几乎一样，这改变了 §5 的写法

| 平台 | `s₃₂` |
|---|---|
| aarch64 CPU（128 核） | 2.10 |
| Mars X201 | 2.29 |

差 9%。**"两个平台的最优精度不同"这个说法在 FP32/FP64 这一档上不成立。**
真正会分化的是 11 位那一档（`s₁₁`）：CPU 没有低精度 ALU（`s₁₁≈1`），
GPU 有张量核（可能 4–16）。相图上两条水平线的差别来自 `s₁₁`，不是 `s₃₂`。

### 4.2 无 root 编译 GPU 内核的完整配方

机器上 `/usr/include/c++` 不存在，`htcc` 会卡在 `<tuple>`。**不需要装包**：

```bash
# 1) 从仓库元数据查到包名
B=https://update.cs2c.com.cn/NS/V10/V10SP3-2403/os/adv/lic/base/aarch64
curl -s "$B/repodata/<hash>-primary.xml.gz" -o /tmp/p.xml.gz
python3 -c "import gzip,re;d=gzip.open('/tmp/p.xml.gz','rt',errors='ignore').read();
[print(re.search(r'<location href=\"([^\"]+)\"',m.group(1)).group(1))
 for m in re.finditer(r'<package[^>]*>(.*?)</package>',d,re.S)
 if '<name>libstdc++-devel</name>' in m.group(1)]"
# → Packages/libstdc++-devel-7.3.0-...ky10.aarch64.rpm

# 2) 下载并解到 $HOME（无需 root）
mkdir -p ~/local-cxx && cd ~/local-cxx
curl -sO "$B/Packages/libstdc++-devel-7.3.0-...rpm"
rpm2cpio *.rpm | cpio -idm
ln -sf /usr/lib64/libstdc++.so.6 lib/libstdc++.so

# 3) 编译（注意头目录是 7.3.0，不是 7）
H=$HOME/local-cxx
/opt/hpcc-3.5.3/htgpu_llvm/bin/htcc -O3 -std=c++14 \
  -isystem $H/usr/include/c++/7.3.0 \
  -isystem $H/usr/include/c++/7.3.0/aarch64-linux-gnu \
  -isystem $H/usr/include/c++/7.3.0/backward \
  -I/opt/hpcc-3.5.3/include -o ~/lu_bench_gpu lu_bench_gpu.cu \
  -L$H/lib -lstdc++ -L/opt/hpcc-3.5.3/lib -lhcruntime -lm

# 4) 跑
export LD_LIBRARY_PATH=/opt/hpcc-3.5.3/lib:$LD_LIBRARY_PATH
~/lu_bench_gpu 8192
```

**注意**：`hcMemcpy(dst, src, bytes, kind)` 是 (目的, 源) 顺序，写反会静默失败并输出
`hcErrorInvalidValue`——第一版自检就是这么挂的。
