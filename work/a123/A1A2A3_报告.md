## 0. 结论摘要

**能站住的（A/B 级）**

1. **存储**：fp32 因子比 fp64 小 **1.23–2.12×**。这是可复算的字节数，不受测量噪声影响。
2. **并行因子的竞态已修复**（根因明确：读后清零竞争 + 计数未钳位）。
   **但失败率强烈依赖机器负载**：高负载下 50%/70%/90%，空闲 4 卡并发下旧二进制 96.25%、新二进制 100%
   ——差异不显著（p≈0.12），所以修复依据是**根因分析**而非前后对比（§5.1.1）。
3. **统计口径**：重复 10 次实测 CV 为 **1.3–3.8%**，所有单点数字都应改为区间（§9）。

**有明确边界的（B−/C 级）**

4. **fp32 的收益只在存储，不在时间**：串行因子上**最多快 2.7%**（四矩阵 95% CI 上界 ≤1.027，bandgap 甚至慢 2.4%）。
   **边界**：只测了串行因子；并行 fp32 因子不存在，而带宽收益恰恰要靠它兑现（§3、§7）。
5. **fp32 + 迭代精化能救精度**：pg2k/pg5k/pg10k 上 2 轮把 1.2e-7 压到 1e-13~1e-11，
   代价 **2.0–3.3×** 三角求解时间（中等矩阵 2.02–2.03×，小矩阵因固定开销达 3.3×）。**边界**：这是 Richardson，**不是** GMRES-IR（§1、§2）。
6. **病态矩阵上 fp32 因子不可救**：flash-adc 的 fp32 因子直接解残差 **1.04e10**（因子已坏）；
   接上 **GMRES-IR** 后 206 轮反而发散到 3.78e46（§17）。但同一矩阵上 **fp64 因子 + GMRES-IR
   只要 8 轮 / 50.6 ms 就到 1.05e-6**（Richardson 20 轮仍停在 1.75e-6）——
   **方法有效，瓶颈是预条件子精度，不是迭代格式。**
7. **规模上限**：PAR 因子需 `12n+256` B 共享内存，n=10,082 时报 `hcFuncSetAttribute → hcErrorInvalidValue`；
   上限落在 5k~10k 之间（**未直接查询设备属性**，属推断）。ST 能到 10k，但单次 **130–140 s**（§4）。

**必须改口径的（实测否决或不利）**

8. **外部基线**：并行因子比单线程 KLU 慢 **97–426×**，串行因子慢 1,206–8,865×（§10）。
   → 所有"加速比"都是**同实现内部**的相对值，不能作为性能成果；本工作应定位为**可行性/工程性**成果。
9. **补 BTF、换 AMD 都救不了**：pg 系列 BTF 是单块（占 99.6%，0 收益）；只换列序 AMD 反而 **−4%**；
   填充差来自"**对称置换**"，而我们的内核没有行置换（§11）。

## 1. 方法

在原基准上增加两段迭代精化。**注意：这是"一步 Richardson 迭代"，不是 GMRES-IR**——
预条件子直接作用于残差、没有内层 GMRES，收敛域比文献里的 GMRES-IR 小得多（后果见 §2 读法、§8 第 4 条）：

```
x0 = 0
r_k = b - A x_k          (fp64，host SpMV，用原矩阵)
if ||r_k||/||b|| < 1e-10 或 > 1e8 → 停
δ_k = M^-1 r_k           (预条件子 = 三角求解，因子分别为 fp32 / fp64)
x_{k+1} = x_k + δ_k
```

- `DSH_IR=1` 开启；`[fp32 IR]` 用 **fp32 因子** + fp64 残差；`[fp64 IR]` 用 **fp64 并行因子** + fp64 残差
- 收敛判据 `DSH_IR_TOL`（默认 1e-10）、上限 `DSH_IR_MAXIT`（默认 20）；残差 >1e8 或 NaN 即判发散停止
- `DSH_SKIP_PAR=1` 跳过并行因子段（n 过大时）
- 计时口径与原基准一致：`cudaEvent` 内核级，warmup 后取 reps 次最优；IR 段记「每轮三角求解时间之和 + host SpMV 时间」

## 2. A1　迭代精化（Richardson 形式）实测

| 矩阵 | n | fp32 直解残差 | fp32+IR 轮数 | fp32+IR 时间 (ms) | fp32+IR 残差 | fp64+IR 轮数 | fp64+IR 时间 (ms) | fp64+IR 残差 |
|---|---|---|---|---|---|---|---|---|
| sky130_bandgap | 113 | 3.06e-03 | 3 | 1.26 | 3.96e-11 | 1 | 0.42 | 3.28e-12 |
| sky130_flash | 989 | 1.04e+10 | 1（发散） | 3.31 | 1.04e+10 | 20（未达 tol） | 65.79 | 1.75e-06 |
| pg2k | 4050 | 1.30e-07 | 2 | 27.09 | 9.06e-13 | 1 | 13.60 | 6.65e-16 |
| pg5k | 5000 | 1.21e-07 | 2 | 34.53 | 2.02e-11 | 1 | 17.01 | 6.23e-16 |
| pg10k | 10082 | 1.27e-07 | 2 | 71.21 | 8.05e-13 | n/a（并行因子超限） | — | — |

**读法**

- 良态/中等矩阵：**2 轮**足够，把 1e-7 压到 1e-12 量级；每轮成本 ≈ 一次三角求解（13–35 ms）。
  相对 fp64 直解的三角求解，IR 总成本为 **2.04 ± 0.05×**（pg2k，10 次重复）——这是"用精度换存储"的实际代价。
- sky130-flash-adc 是反例：fp32 因子精度崩塌（1e10），**任何**基于该因子的精化都无意义；
  fp64 因子 + Richardson 到 1.75e-6 就停住，而 fp64 直解本身是 6.1e-7 —— 同一量级，说明到了因子精度地板。
  20 轮是在空转（tol=1e-10 不可达）。
  **这条不能推广成"IR 救不了病态矩阵"**：文献里的 GMRES-IR 用内层 GMRES 扩大收敛域
  （Carson & Higham, SIAM J. Sci. Comput. 2018），我们没实现它。

- **存储**：稳定在 1.5× 左右（10 ↔ 12 B/nnz；flash-adc 因 fp32 填充更少达到 2.12×）。

**随规模的变化**

| 量 | 从 n=4050 → 10082（矩阵规模 2.5×） | 指数 |
|---|---|---|
| ST 因子 | 22.6 s → 139.6 s（**6.2×**） | 仅 4 点、跨负载采样，**不足以定指数** |
| ST 三角求解 | 127.8 → 394.6 ms（3.1×） | ≈ n^1.24 |
| PAR 三角求解（n≤5k） | 13.5 → 16.6 ms | 近似常数（启动开销主导） |

**两堵墙**

1. **共享内存墙（PAR 因子）**：`LU_PAR_SHARED_BYTES(n) = 12n + 256` B。
   n=5,000 → 58.8 KB（可用）；n=10,082 → **118.3 KB**（超限），报
   `hcFuncSetAttribute: Returned hcErrorInvalidValue`。
   → 由"12n+256 与 64 KB"反推，上限约 **n ≈ 5.4k**；**该数值是推断**，
   未调用 `cudaDeviceGetAttribute(cudaDevAttrMaxSharedMemoryPerBlockOptin)` 实测设备上限。
2. **串行时间墙（ST 因子）**：n=10,082 单次分解 **130–140 s**，增长明显超线性
   → pg25k / pg50k（n=25088 / 49928）在 ST 下预计 **10–40 分钟/次**，**本轮未跑**（判定为不可用而非未测）。

**结论**：现有实现的可用工作区间是 **n ≲ 5k（并行路径）**；n > 10k 必须走
"多 block 波次调度"的重写（`mp_bench/multiblock_lu.cu` + `design/m3_multiblock_sched.md` 已有骨架，
但同样以 `extern __shared__ double x[]` 的方式按 n 分配共享内存，也会撞同一堵墙，需要重新设计）。

## 5. 三个需要单独处理的发现

### 5.1 fp64 并行因子竞态：已定位并修复（2026-10-31）

**修复前**（只跑 PAR 段，重复运行；判"成功"= rc=0 且残差 < 1e-5）：

| 矩阵 | 次数 | 成功 | 硬失败（rc≠0） | 静默错误（rc=0 但结果错） |
|---|---|---|---|---|
| pg2k | 20 | 10（50%） | 9（4 次 `illegal memory access`、5 次伪 `singular at column`） | 1 |
| pg5k | 10 | 7（70%） | 2 | 1（残差 **2.543e+12**） |
| sky130-flash | 10 | 9（90%） | 0 | 1（残差 **72.2**） |

**根因（两处，都在 `lu_factor_par_kernel` 的结构 BFS 里）**

1. **读后清零竞争**（主因）。每层 BFS 结束时，旧代码是"**每个线程**先读 `cnt[CNT_NXT]`、再把它写 0"：

   ```c
   curcnt = cnt[CNT_NXT];      /* 256 个线程都读 */
   cnt[CNT_NXT] = 0;           /* 256 个线程都写 */
   __syncthreads();
   ```

   快的线程先清零，慢的线程随即读到 **0** → 认为这一层没有新节点 → **BFS 提前结束**，
   该列的可达集不完整 → L/U 结构缺项。轻则因子数值错（静默错解），重则某列完全没候选主元（伪奇异）。

2. **`curcnt` 未钳位**。`cnt[CNT_CUR]` 只保证"不往缓冲区写过界"，但计数本身可以超过
   `LU_PAR_CAP=1024`；读取端直接用 `for (t = 0; t < curcnt; ...)` 遍历 `GFRONT(curbase + t)`，
   t ≥ 1024 时读到 frontier 窗口之外（JLIST 区/越界）→ 拿到的行号是垃圾 →
   `pinv[垃圾]` → **非法访存**。

**修复**（`lu_gpu_par.cu`，备份 `~/Huangcw/backup/lu_gpu_par.cu.orig_20261030`）

```c
/* 1) 先读后清，单写者清零 */
int nextc = cnt[CNT_NXT];
__syncthreads();                 /* 等所有线程读完旧值 */
if (tid == 0) cnt[CNT_NXT] = 0;
__syncthreads();
curcnt = (nextc > LU_PAR_CAP) ? LU_PAR_CAP : nextc;

/* 2) 入口处钳位 */
int curcnt = cnt[CNT_CUR];
if (curcnt > LU_PAR_CAP) { curcnt = LU_PAR_CAP; cnt[CNT_OVF] = 3; }
```

并新增 `if (cnt[CNT_OVF] == 3) break;`，让结构溢出在 BFS 内立即收敛而不是继续跑脏数据。

**验证（同一套脚本，修复后重跑 40 次）**

| 矩阵 | 修复前 | 修复后 |
|---|---|---|
| pg2k | 10/20 = **50%** | **20/20 = 100%** |
| pg5k | 7/10 = **70%** | **10/10 = 100%** |
| sky130-flash | 9/10 = **90%** | **10/10 = 100%** |

40/40 全过，且**成功时残差与修复前完全一致**（6.651e-16 / 6.226e-16 / 6.095e-07），
说明修复只是去掉了偶发破坏，没有改变数值路径。

**对数字的影响**：A1/A2/A3 三张表已用修复后的实现整体重测（4 个矩阵各 1 次即成功），
与修复前"取成功那次"的数值差异在测量噪声内（例：pg2k 的 IR32 29.67 → 27.09 ms，
PAR 因子 729 → 747 ms），**没有发现系统性偏差**。

### 5.1.1 重要修正：失败率强烈依赖机器负载，不是二进制的固定属性

A3（4 卡并发压测）本来是想看"并发会不会更容易出错"，结果**反过来**：

| 条件 | 二进制 | pg2k | pg5k |
|---|---|---|---|
| 单卡，**机器高负载**（14:1x，别队 ngspice 持续跑，load 8–20） | 旧 | 10/20 = **50%** | 7/10 = **70%** |
| 4 卡并发，**机器空闲**（17:35） | 旧 | 40/40 = 100% | 37/40 = **92.5%** |
| 4 卡并发，**机器空闲**（17:38） | 新 | 40/40 = 100% | 40/40 = 100% |

**这意味着"修复前 50% → 修复后 100%"是被负载混淆的**：

- 空闲条件下旧二进制是 **77/80 = 96.25%**，新二进制 **80/80 = 100%**（p ≈ 0.12）。
  后续又做了 **N=200 对的受控对照**（§16）：旧 196/200 = 98%、新 200/200，
  单组 p = 0.062，**合并后 p = 0.0075** —— 见 §16。
- 高负载下的 50%/70% 不能与空闲下的 100% 直接对比。

**那修复的依据是什么？** 是**根因**：读后清零竞争（快的线程清零、慢的线程读到 0 → BFS 提前结束）
与 `curcnt` 越界读。这两处是确定性的逻辑错误，与负载无关，只是**触发概率**受调度影响。
所以正确的表述是：

> 修复消除了两处确定的并发缺陷；在空闲条件下观测到的收益（96.25% → 100%）**样本量不足以达到统计显著**，
> 但修复本身有代码级依据，且未引入回归（成功样例残差逐位一致）。

**对论文的含义**：如果要写"可靠性提升"，需要**在受控负载下**做对照（例如固定在 load=X 时跑旧/新各 N 次），
否则这个数字站不住。当前 §5.1 的表格应理解为"高负载下的故障率上界"，而不是"平均故障率"。

### 5.2 Richardson 的收敛上限 = 预条件子的精度

sky130-flash-adc 上 fp64 因子 + IR 跑 20 轮仍在 1.75e-6，而 fp64 直解是 6.1e-7。
说明 Richardson 型 IR 在预条件子精度不足时会进入"抖动平台"，**加轮数无益**；
需要更准的因子（或真正的 GMRES + 更高精度内层），这与 `test_lu_gpu_ir64.cu` 的设计意图一致。

| 与 RTX 3060 的跨平台对比 | **未做**：现有 2 个矩阵、无方差，证据等级 D。 |

## 8. 结论强度自评（批判性）

按"证据能不能撑住结论"逐条打分。**强度**：A=可复算的确定性事实；B=同机实测、有重复；C=单次实测/单一实现；D=推测。

| # | 结论 | 强度 | 主要问题 | 同行工作对照 |
|---|---|---|---|---|
| 1 | fp32 因子存储小 1.23–2.12× | **A** | 无（字节数可复算） | — |
| 2 | 并行因子比串行快 21.9–33.7×（三矩阵，逐次比值） | **B−** | 这是**同实现内部**的相对值；补了外部基线后（§10），我们的并行因子比单线程 KLU **慢 97–426×** | KLU（Davis & Palamadai Natarajan, TOMS 2010）；GLU（IEEE TVLSI 2015） |
| 3 | fp32 因子"不提速"（≤1.04×，95% 上界） | **C** | **只在串行左看因子上测过**，而串行因子是延迟/依赖受限，本来就不该受益于位宽；缺 fp32 并行因子 | 混合精度稀疏直接法的收益逻辑是带宽与容量（Amestoy 等，HAL hal-03536031）；本结论不能外推到"fp32 无用" |
| 4 | "IR 的效果受限于预条件子精度" | **B** | 已实测 GMRES-IR（§17）：fp32 因子坏掉时 GMRES 也发散（3.78e46）；fp64 因子时 GMRES 8 轮收敛而 Richardson 20 轮停滞 | Carson & Higham（SIAM J. Sci. Comput. 2018）；GMRES-IR 扩展收敛域但不创造精度 |
| 5 | "ST 因子增长超线性" | **C** | 只有 5 个点（113/989/4050/5000/10082），且**跨不同负载**采；PAR 在 n>5.4k 缺失，所谓规模曲线其实是串行曲线 | 拟合指数应报置信区间；4 点拟合指数区间极宽，不应写成 ≈n² |
| 6 | 共享内存墙 n≈5.4k | **B−** | 12n+256 B 是确定的，但"设备上限 64 KB"是**从报错反推**，没有打印 `cudaDeviceGetAttribute(cudaDevAttrMaxSharedMemoryPerBlockOptin)` | CUDA 编程指南：opt-in 上限因架构而异（48/64/96/164/227 KB），必须实测 |
| 7 | 竞态修复后 40/40 通过 | **B** | 3 矩阵、单机、单 runtime；对"修复有效"足够（二项检验 p≈1e-6），对"并行因子可靠"是过度推广 | 并行归约/散射的位级不确定性是已知问题（Demmel & Nguyen, 可复现求和），修复后仍不保证 bitwise 一致 |
| 8 | X201 vs RTX 3060 跨平台对比 | **D** | 2 个矩阵、两台机器、不同时间、无方差 | 跨平台对比必须同矩阵同算法同口径并报区间 |
| 9 | 瓶颈**不是带宽**，是**单实例并行度不足** | **B** | 实测峰值 1.45 TB/s；按数据量上界，内核带宽利用率 <0.1%，不可能是带宽受限 | Roofline（Williams, Waterman & Patterson, CACM 2009）；§15 给出两条独立证据 |

### 8.1 方法论层面的三个硬伤

1. **单点计时**。所有数字原先都是 best-of-N（min），这是最乐观的估计。Hoefler & Bell（SC'15《Scientific Benchmarking of Parallel Computing Systems》）明确反对这种做法，建议报中位数/百分位与置信区间。
   本轮 B2 实测：即使在空闲机器上，同一配置重复 10 次的 **CV 也有 1.3–3.8%**（见 §9），所以**任何小数点后两位的单点数字都是过度精确**。
2. **外部基线（已补，结论不利）**。§10 补了单线程 KLU：我们的并行因子慢 97–426×。
   所以"29×"只能说明并行化在同实现内有效，不能说明绝对性能位置。
3. **没有 Roofline 定位**。既然核心论点是"带宽/访存受限"，就必须给出实测带宽与峰值带宽的比值，否则"受限"只是推断。

### 8.2 结论该怎么改写（示范）

- 原："fp32 因子不提速。" → 改："**在本实现的串行左看因子上**，fp32 存储不带来时间收益（比值 0.995 ± 0.023，95% 上界 1.018），因为该内核受串行依赖限制；其收益体现为存储 1.5× 与带宽减半，**需并行因子实现才能兑现**。"（对照 Amestoy 等关于带宽收益的论述）
- 原："IR 救不了病态矩阵。" → 改："**简化的一步 Richardson 精化**在 sky130-flash 上发散，说明该实现不足以处理该矩阵；文献中的 GMRES-IR 通过内层 GMRES 扩大收敛域（Carson & Higham 2018），本实验**不构成对 IR 方法的否定**。"
- 原："规模曲线显示 ST 因子 ~n²。" → 改："在 4 个规模点上，串行因子耗时从 22.8 s 增至 139.6 s（规模 2.5×），**增长明显超线性**；点数不足以确定指数。"

### 8.3 补哪些实验才能把结论做硬

## 11. "补 BTF"可行性评估（实测否决）

用 KLU 自带的 `btf_order` 对我们的矩阵做结构分析（`klu_base/btf_probe.c`，链接同一份 `libKLU.a`）：

| 矩阵 | n | BTF 块数 | 最大块 | 最大块占比 | off-diagonal nnz | lnz+unz（AMD+BTF） | lnz+unz（AMD，关 BTF） |
|---|---|---|---|---|---|---|---|
| sky130_bandgap | 113 | 6 | 101 | 89% | 149 | 638 | — |
| sky130_flash | 989 | 41 | 60 | 6% | 1,697 | 5,536 | — |
| pg2k | 4,050 | 9 | 4,034 | **99.6%** | **0** | 206,808 | **206,808** |
| pg5k | 5,000 | 11 | 4,980 | **99.6%** | **0** | 254,082 | **254,082** |
| pg10k | 10,082 | 20 | 10,044 | **99.6%** | **0** | 622,374 | 622,374 |

### 结论 1：BTF 对 pg 系列**零收益**

三个 pg 矩阵都是"一个巨块 + 几个 2–4 阶孤立节点"，`nzoff = 0`（没有块外非零）。
**开关 BTF 填充量完全一样**（pg2k 都是 206,808）。因为 BTF 的价值来自"把大矩阵拆成互不依赖的小块"，
而这三个矩阵在结构上是**不可约**的——它们本来就是一块。

### 结论 2：填充差距**不是"换个排序函数"能拿到的**（详见 11.1/11.2）

KLU 的 206,808 是在 **对称置换 `A(P,P)`**（行、列同时换）+ 它自己的主元策略下得到的。
把 AMD 只当"列序"接进我们的内核（A'A 上跑 `amd_order`），实测得到 **415,007 —— 反而差 4%**。
所以 1.68× 藏在"对称置换"里，而我们的内核**没有行置换**。

### 结论 3：真正的差距是内核效率，差 50×

同排序（都用 COLAMD）下的对照，才能把"填充"和"内核效率"分开：

| | 填充 nnz | 分解时间 | 每 1000 填充项 |
|---|---|---|---|
| KLU（单线程 CPU，COLAMD） | 346,573 | 15.67 ms | **0.0452 ms** |
| 我们 PAR（COLAMD） | 397,976 | 754.5 ms | **1.90 ms**（**42×**） |
| 我们 ST（COLAMD） | 397,976 | 22,083 ms | 55.5 ms（1,228×） |

**填充只差 1.15×，时间差 48×** —— 差距的主体是内核效率，不是填充，也不是排序。
BTF 既改不了这个差距（pg 系列单块），换排序也改不了（实测 −4%）。

### 结论 4：三角求解的差距（46×）比因子更值得先修

KLU 0.30 ms vs 我们 13.9 ms。原因是逐层 n 次 `__syncthreads()`（n=4050 → 4050 次同步），
而 KLU 用块化稠密三角求解。这一块可以独立于因子改造，收益确定。


### 11.1 实测：把 AMD 换进来会怎样（2026-10-31）

我按两种方式把 AMD 接进 `mp_lu_bench_ir`（`DSH_ORDER=klu_amd|amd_ata`）：

**(a) 直接用 KLU 分析出来的列序 `Q`** → 填充**恶化 3×**：

| 矩阵 | COLAMD（现状） | 用 KLU 的 Q |
|---|---|---|
| pg2k | 397,976 | **1,180,372** |
| pg5k | 533,164 | **1,531,941** |

原因：KLU 的 `Q` 是**与行序 `P` 成对**的（对称置换 `A(P,P)` + 块三角化），单拿列序用，
对"自己选主元、不做行置换"的内核就是错的。

**(b) 自己在 `A'A` 结构模式上跑 `amd_order`（这才是 COLAMD 的同语义替代）** → **没有收益**：

| 矩阵 | COLAMD 填充 | AMD(A'A) 填充 | COLAMD 分解 | AMD(A'A) 分解 |
|---|---|---|---|---|
| pg2k | 397,976 | 415,007（**+4.3%**） | 754.5 ms | 772.2 ms |
| pg5k | 533,164 | 546,000（**+2.4%**） | 1,038.2 ms | 1,039.9 ms |

**(c) KLU 内部的同框架对照**（同一份 KLU，只换排序）：

| 矩阵 | AMD 填充 | COLAMD 填充 | 比值 | AMD 分解 | COLAMD 分解 |
|---|---|---|---|---|---|
| pg2k | 206,855 | 346,573 | 1.68× | 7.75 ms | 15.67 ms |
| pg5k | 255,271 | 471,221 | 1.85× | 9.56 ms | 23.94 ms |
| pg10k | 622,587 | 1,141,757 | 1.83× | 31.5 ms | 84.0 ms |

### 11.2 修正后的结论：填充差不是"排序"，是**缺少对称置换**

把三个数字放在一起：

```
我们的 COLAMD          397,976
KLU + COLAMD           346,573   ← 同排序下我们多 1.15×（主元选择差异）
KLU + AMD              206,855   ← 1.68× 来自 AMD，但那是带 P=Q 的对称置换
我们的 AMD（列序）      415,007   ← 只换列序：没有收益
```

**"换 AMD 排序"不是半天能拿的 1.9×**。真正的收益来自**对称置换 `A(P,P)`**（行、列同时换），
而我们的内核是"固定行序 + 自己选主元"，拿不到这个收益。要拿到，必须给内核加**行置换支持**——
这会动到主元位置语义、`Li` 重映射、三角求解的序，属于结构性改动，不是换排序调用。

**同时**：即使填充追到 KLU 的水平，同排序下的时间比仍是 **754.5 ms vs 15.67 ms ≈ 48×** ——
内核效率差是独立且更大的问题。

| 选项 | 收益 | 成本 | 结论 |
|---|---|---|---|
| 补 BTF | pg 系列 0% | 1–2 周 | **不做** |
| 只换列序（AMD on A'A） | **−4%**（更差） | 半天 | **已实测否决** |
| 加行置换 + 对称 AMD | 填充 ~1.7× | 3–4 周，动内核语义 | 收益确定但不足以翻盘 |
| 块化三角求解 | 5–10× | 1–2 周 | **优先做** |
| 块化因子内核（含 BLAS3） | 需追 48× | 1–2 个月 | 与论文周期冲突 |
| 论文定位改为"可行性/精度" | 0 | 0 | **现实选择** |

**一句话**：BTF 无效、只换列序无效；填充的 1.7× 藏在"对称置换"里，需要行置换支持；
但即便拿到，内核仍有 48× 的差距——**性能叙事救不回来，结论应改口径**。

### 12.1 两条必须写进论文的**口径不对称**

1. **计时口径不对等**。我们的因子/三角时间是 **`cudaEvent` 包住 kernel**（不含分配与 H2D）；

## 13. 四卡并发扩展实验（A1，2026-10-31 17:32）

**问题**：单卡 GPU 利用率只有 23.4%，说明单实例喂不饱一张卡。那么**多实例/多卡能不能线性填满**？
如果能，"低利用率"就不是缺陷，而是"可并发的资源"。

**设计**：同一矩阵、同一配置（`max_n_st=0`，只跑 PAR 段，`reps=3`），
1/2/4 个实例分别在 1/2/4 张卡上**同时启动**；每个组合重复 3 轮。

| 矩阵 | 实例数 | 每实例 PAR 因子 | 端到端墙钟 | 聚合吞吐 | 扩展效率 |
|---|---|---|---|---|---|
| pg2k | 1 | 739.7 ms | 4,480 ms | 0.223 inst/s | 100% |
| pg2k | 2 | 737.4 ms | 4,511 ms | 0.443 inst/s | **199%** |
| pg2k | 4 | **738.4 ms** | 4,525 ms | 0.884 inst/s | **396%** |
| pg5k | 1 | 987.9 ms | 5,838 ms | 0.171 inst/s | 100% |
| pg5k | 2 | 1,007.5 ms | 5,865 ms | 0.341 inst/s | **199%** |
| pg5k | 4 | **1,003.8 ms** | 5,942 ms | 0.673 inst/s | **393%** |

### 结论

1. **近乎完美线性**：4 卡扩展效率 **393–396%**（理想 400%）。
2. **每实例耗时几乎不变**：pg2k 739.7 → 738.4 ms（**+0%**），pg5k 987.9 → 1003.8 ms（**+1.6%**）。
   说明**卡间没有互相拖慢**——每张 Mars X201 有独立 HBM，实例之间不争带宽，驱动也没有串行化。
3. **对"23.4% 利用率"的重新解释**：单实例占用率低，是**单实例内部并行度不足**（逐层 barrier + 列间串行循环），
   不是"GPU 资源不够"。多个实例可以几乎无损地把 4 张卡填满——**低占用率是可并发的资源，不是浪费**。
4. **注意口径**：端到端墙钟里 CPU 参考解（`cpu_lu_ref`，用于正确性对照）占了约 3.5 s，
   而 GPU 因子只有 0.74 s。所以"3.96× 端到端扩展"里也含了 CPU 侧的并行（128 核）。
   **真正干净的证据是"每实例因子时间不退化"**——GPU 侧没有争用。

**对论文的用法**：可以写"该实现具备**近线性吞吐扩展能力**（4 卡 3.93–3.96×），
瓶颈在单实例内部结构（§8 第 9 条）而非资源不足"；但不能据此说"单卡性能好"——
单卡绝对性能仍比 KLU 慢两个数量级（§10）。

## 15. Roofline：实测峰值带宽与"是不是带宽受限"的判定（2026-10-31 19:05）

工具：`bw_probe.cu`（自写三个内核，512 MB/数组，`cudaEvent` 计时，warmup+10 次取最优）。

### 15.1 实测峰值

| 内核 | 访存模式 | 耗时 | 带宽 |
|---|---|---|---|
| copy（`b[i]=a[i]`） | 纯流式 | 0.742 ms | **1,446 GB/s** |
| triad（`c=a+2b`） | 流式三数组 | 1.118 ms | **1,441 GB/s** |
| scatter（`x[idx[i]] -= v[i]`，idx 全域随机） | **最坏随机散射** | 158.7 ms | **6.77 GB/s** |

→ 这张卡的流式峰值约 **1.45 TB/s**；把访问模式换成"全域随机散射"，带宽直接掉到 **6.77 GB/s（0.47%）**，差 **213×**。

### 15.2 我们的 LU 因子到底吃了多少带宽：**测不准，但可以定上界**

两个采样工具在这个内核上给出**互相矛盾**的结果：

| 工具 | 空闲 | 因子运行期间 |
|---|---|---|
| `ht-smi --show-hbm-bandwidth`（1 s 粒度） | 1 MB/s | **峰值 332 MB/s** |
| `lib_bw_sample.py`（htsml 绑定，0.02 s） | 2 MB/s | 峰值 **197,097 MB/s** |

后者按积分算等于"单次因子运行搬运 994 MB"——而整个因子（L+U 填 398k）只有 **4.8 MB**，
等于要重读 200 遍，物理上不可能。**所以 lib 采样的量纲/口径有误，不能引用**；
ht-smi 的 332 MB/s 也受 1 s 粒度限制（因子只有 0.73 s），只能当下界参考。

**改用数据量做上界**（不依赖采样）：

```
单次因子输入+输出：A 0.2 MB + L/U 4.8 MB ≈ 5 MB
即使左看算法把 L 列重读 100 遍 → 500 MB
500 MB / 0.73 s ≈ 685 MB/s ≈ 峰值的 0.05%
```

→ **无论怎么算，这个内核的带宽利用率都不超过峰值的 0.1%**。

### 15.3 结论：**不是带宽受限，是并行度/延迟受限**

这条**推翻了 §8 第 9 条原来的说法**（"散射随机访存主导、有效带宽约 1 GB/s"）：

- "~1 GB/s" 这个量级本身可能是对的，但**用它解释性能就错了**——1 GB/s 是峰值的 **0.07%**，
  不可能是"带宽把我卡住了"。真正的限制是：
  1. **单 block × 256 线程**（`<<<1,256>>>`），整卡只用一个 SM；
  2. **列间严格串行**（第 k 列依赖前面所有列），没有跨列并行；
  3. 与实测 23.4% 的 GPU 利用率、以及"4 卡并发时每实例耗时不变（+0%）"三者一致。

**改写后的表述**（建议直接替换 §8 第 9 条）：

> LU 因子内核的带宽利用率低于峰值的 0.1%（实测峰值 1.45 TB/s），
> 因此性能瓶颈**不是 HBM 带宽**，而是**单实例并行度不足**（单 block、列间串行）。
> 这解释了 23.4% 的占用率，也解释了为什么多卡/多实例能近线性扩展（§13）。

**顺带**：§8 第 9 条的强度从 **D（倒推）** 升到 **B**（有实测峰值 + 数据量上界两条独立证据），
但**结论内容变了**——这是本轮唯一一条"做了实验反而否定原假设"的。

## 17. GMRES-IR 实测：能不能把 fp32 因子救回来？（2026-10-31 20:05）

**动机**：§5.2 只测了 Richardson（一步迭代），当时的结论"IR 停在 1.75e-6"被质疑为"实现缺陷而非方法极限"。
本轮把文献里的 **GMRES-IR**（右预条件、m=50、最多 7 次 restart、两遍修正 Gram-Schmidt）接进同一基准，
预条件子分别用 fp32 因子和 fp64 因子，直接对比。

| 矩阵 | Richardson(fp32) | Richardson(fp64) | **GMRES-IR(fp32)** | **GMRES-IR(fp64)** |
|---|---|---|---|---|
| sky130_bandgap | 3 轮 / 1.26 ms / 3.96e-11 | 1 轮 / 0.36 ms / 3.28e-12 | 3 轮 / 1.64 ms / **2.95e-12** | 1 轮 / 0.90 ms / 2.58e-12 |
| **sky130_flash** | 1 轮 / 3.3 ms / **1.04e+10（发散）** | 20 轮 / 66.1 ms / 1.75e-06 | 206 轮 / 718 ms / **3.78e+46（更糟）** | **8 轮 / 50.6 ms / 1.05e-06** |
| pg2k | 2 轮 / 27.2 ms / 9.06e-13 | 1 轮 / 13.7 ms / 6.65e-16 | 2 轮 / 42.5 ms / 9.05e-13 | 1 轮 / 28.6 ms / 6.72e-16 |

### 结论

1. **GMRES-IR 救不回 fp32 因子——这是本轮最直接的答案。**
   flash-adc 上 fp32 因子的直接解残差是 **1.04e10**，说明**因子本身已经坏了**（不是"精度低"，是错）。
   在坏预条件子上跑 GMRES，迭代 206 次后残差反而涨到 **3.78e46**——内层 GMRES 只会放大坏方向。
   → **"能不能用 fp32 因子救回来"：不能。** 前提是因子可用；这个矩阵的 fp32 因子不可用。

2. **但对 fp64 因子，GMRES-IR 明显优于 Richardson**：flash-adc 上 **8 轮 50.6 ms 到 1.05e-6**，
   而 Richardson 跑了 20 轮还停在 1.75e-6。GMRES-IR 确实扩展了收敛域——**只是它扩展不了预条件子的精度**。

3. **良态矩阵上 GMRES-IR 反而更慢**：pg2k 上 1 轮 28.6 ms，Richardson 同样 1 轮只要 13.7 ms
   （多一次 M⁻¹ 作用 + 正交化开销）。→ 正确策略是**自适应**：先 Richardson，停滞了再上 GMRES-IR。

4. **顺带修正 §0 第 6 条/§8 第 4 条的表述**：之前说"我们没实现 GMRES-IR，所以不能否定 IR 方法"——
   现在实现了，结论是"**方法有效，但受限于预条件子精度**"。这条从"无法判断"变成"有实测支持的判断"。

**局限**：只测了 3 个矩阵；m=50/7 次 restart 是照搬参考实现，没调参；
flash-adc 的 fp32 因子**为什么**坏（是 κ 太大还是主元选择问题）没查——这是下一个该问的问题。
